# 连续丢包自动暂停分流

后台「系统设置 → 多节点 Responses 分流」提供「连续丢包自动保护」开关及「丢包暂停时长（分钟）」。默认开启、5 分钟，时长可设为 1–120 的整数。修改时长用于下次触发或续期，现有暂停保持原截止时间；关闭开关会清除丢包暂停。手动目标比例保持原值。

## 判断依据

控制节点读取当前监控地址的 `/api/records/ping?uuid=…&hours=1`，使用原始 ICMP 探测记录。每个 `task_id` 代表一个独立探测目标，至少需要两个目标，多数票通过（3 个目标需 2 个，4 个目标需 3 个）。`value < 0` 为失败，`0` 是成功的亚毫秒探测。首页一小时汇总丢包率不作为触发依据。

一个目标符合以下任一条件才算持续严重丢包：

- 最近两次连续探测均失败。
- 最近 6 次探测构成前后两个各 5 次的滑动窗口，两个窗口均至少失败 2 次（40%），且最近两次仍有失败。

多数目标符合上述条件，且另有探测恢复、监控新鲜、未被流量保护摘除、未在暂停中的正权重节点，才新增暂停。多个节点或探测目标一起异常而没有健康替代时显示「暂无健康替代节点」，避免集体摘流。

样本按时间排序并去重，剔除空值、其他节点记录和超过当前时间 15 秒的记录。相邻样本间隔须为配置探测间隔的 0.5–1.5 倍；最新样本年龄不得超过探测间隔的 2.5 倍且最多 3 分钟。缺测和监控 API 错误不作为丢包。支持 5–300 秒间隔的 ICMP 任务，其他任务不参与投票。当前监控每 60 秒探测一次，持续全丢包通常在第二个失败样本后触发；控制运行态缓存 30 秒、边缘缓存默认 15 秒带来额外传播时间。

## 暂停与恢复

暂停仅将节点 `effective_weight` 设为 0，`auto_disabled=true`、原因 `packet_loss`。边缘分流会同时避开普通选择与满载兜底；已开始的请求和流继续执行。该保护作用于现有 Worker 管理的 Responses 入口，直接访问节点或其他未走该分流器的路径不在此机制内。

暂停截止前不提前恢复。到期后，多数目标连续三次成功且没有目标仍处于持续严重丢包，才恢复目标权重；持续严重丢包并出现新的探测样本时续期。数据不足、缺测或轻度异常时保持暂停并显示「等待网络恢复确认」。重复读取同一批样本不会延长截止时间。

暂停截止时间和触发样本时间存入独立设置 `gateway_routing_packet_loss_state`，按监控地址、节点 ID、源站地址隔离；控制节点重启后继续生效。配置由控制节点维护；此实现沿用当前单控制节点拓扑。流量保护、离线保护和人工零权重仍各自生效。监控整体中断时继续读取持久化暂停，状态存储失败时保留本进程上次确认的暂停并显示状态不可用。

## 接口和验证

`gateway_routing_settings` 新增 `packet_loss_protection_enabled`、`packet_loss_cooldown_minutes`。未携带新字段的旧设置兼容默认值，无数据库结构迁移。

每个运行态节点新增 `packet_loss_state`、`packet_loss_percent`（近期窗口观测比例）、`packet_loss_sample_at`、`packet_loss_paused_until`。管理页显示状态与截止时间，刷新运行态按钮可读取最新结果。恢复后 Worker 根据现有运行态自动重新选择节点，无需改变静态 Worker 权重或重新发布 Worker。

回归覆盖实际 Komari JSON 契约、单目标故障、多数票、窗口边界、零毫秒成功、重复/缺失/陈旧样本、持久化重启、监控中断、配置校验与回显、健康替代节点、手动禁用、零权重兜底、流量保护优先级和边缘摘流恢复。
